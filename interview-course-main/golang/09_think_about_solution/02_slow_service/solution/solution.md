# Решение: Медленный сервис аналитики

## Анализ проблемы

### Корневая причина
Сервис заказов работает **синхронно** с сервисом аналитики:
- ❌ Пользователь ждет результата обработки заказа
- ❌ Обработка заказа ждет результата от аналитики
- ❌ Один медленный сервис блокирует всю цепочку

### Последствия
- **Потеря заказов** — пользователь не получает подтверждение
- **Плохой UX** — долгое время ожидания
- **Потеря денег** — неудавшиеся транзакции
- **Высокая связность** — сервисы сильно зависят друг от друга

---

## Решение 1: Асинхронная обработка через очередь сообщений

### Архитектура

```
+-------+         +---------------+    +------------+    +-------------------+
| User  |         | OrderService  |    | Queue      |    | AnalyticsService  |
+-------+         +---------------+    | (RabbitMQ, |    +-------------------+
|                     |                | Kafka)     |              |
| CreateOrder         |                +------------+              |
|-------------------->|                      |                     |
|                     |                      |                     |
|                     | SaveOrder            |                     |
|                     |------------------    |                     |
|                     |                 |    |                     |
|                     |<-----------------    |                     |
|                     |                      |                     |
|                     | PublishEvent         |                     |
|                     |--------------------->|                     |
|                     |                      |                     |
|<--------------------|                      |                     |
| Order Confirmed     |                      |                     |
|                     |                      | ConsumeEvent        |
|                     |                      |-------------------->|
|                     |                      |                     |
|                     |                      |                     | Process
|                     |                      |                     |----------
|                     |                      |                     |         |
|                     |                      |                     |<---------
|                     |                      |<--------------------|
|                     |                      | Ack                 |
```

### Описание подхода

1. **OrderService** сохраняет заказ в БД
2. **OrderService** публикует событие в очередь (RabbitMQ/Kafka)
3. **OrderService** сразу отвечает пользователю
4. **AnalyticsService** читает события из очереди асинхронно
5. **AnalyticsService** обрабатывает данные в своем темпе

### Плюсы
- ✅ **Низкая латентность** — пользователь получает ответ мгновенно
- ✅ **Отказоустойчивость** — если аналитика недоступна, заказы не теряются
- ✅ **Низкая связность** — сервисы независимы друг от друга
- ✅ **Масштабируемость** — можно добавить несколько consumer'ов
- ✅ **Гарантия доставки** — очередь обеспечивает at-least-once delivery (outbox pattern)
- ✅ **Буферизация нагрузки** — сглаживает пики трафика

### Минусы
- ⚠️ **Дополнительная инфраструктура** — нужна очередь (RabbitMQ, Kafka, NATS)
- ⚠️ **Eventual consistency** — данные в аналитике появляются с задержкой
- ⚠️ **Сложность отладки** — распределенная система сложнее для траблшутинга
- ⚠️ **Дублирование событий** — нужна идемпотентность обработки (inbox pattern)

### Когда использовать
- ✅ Критичен быстрый ответ пользователю
- ✅ Аналитика не влияет на бизнес-логику заказа
- ✅ Возможны задержки в обработке аналитики
- ✅ Требуется высокая пропускная способность


### Выбор очереди

| Решение | Плюсы | Минусы | Когда использовать |
|---------|-------|--------|-------------------|
| **RabbitMQ** | Простота, готовые паттерны, ACK/NACK | Сложность кластеризации | < 50K msg/sec, простые сценарии |
| **Apache Kafka** | Высокая пропускная способность, партиционирование | Сложность настройки | > 100K msg/sec, event sourcing |
| **NATS Streaming** | Легковесность, низкая латентность | Меньше функций | Высокая производительность, простота |
| **Redis Streams** | Простота, уже есть в стеке | Не специализированное решение | Малые объемы, прототипирование |

**Рекомендация:** RabbitMQ для начала, Kafka при масштабировании > 50K msg/sec

## Решение 2: Outbox Pattern (транзакционная очередь)

### Проблема Решения 1
Возможна ситуация:
1. Заказ сохранен в БД
2. Приложение упало ДО публикации события
3. Событие потеряно, аналитика не получит данные

### Архитектура Outbox Pattern

```
OrderService:
┌─────────────────────────────────────┐
│  TransactionBoundary                │
│  ┌──────────────┐  ┌──────────────┐ │
│  │   orders     │  │   outbox     │ │
│  │  table       │  │   table      │ │
│  └──────────────┘  └──────────────┘ │
└─────────────────────────────────────┘
         │                   │
         │                   │ Outbox Worker
         │                   │ reads & publishes
         │                   ▼
         │          ┌──────────────┐
         │          │   Queue      │
         │          │  (RabbitMQ)  │
         │          └──────────────┘
         │                   │
         │                   ▼
         │          ┌──────────────┐
         └─────────►│  Analytics   │
                    │   Service    │
                    └──────────────┘
```

### Таблица `outbox`

```sql
CREATE TABLE outbox (
    id BIGSERIAL PRIMARY KEY,
    aggregate_id VARCHAR(255) NOT NULL,
    aggregate_type VARCHAR(100) NOT NULL,
    event_type VARCHAR(100) NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    processed_at TIMESTAMP,
    processed BOOLEAN DEFAULT FALSE,
    retry_count INTEGER DEFAULT 0
);

CREATE INDEX idx_outbox_processed ON outbox(processed, created_at);
```

### Плюсы
- ✅ **Гарантия доставки** — событие не потеряется
- ✅ **Атомарность** — заказ и событие сохраняются вместе
- ✅ **At-least-once delivery** — повторная публикация при ошибках
- ✅ **Аудит** — история всех событий в БД

### Минусы
- ⚠️ **Сложность реализации** — нужен worker
- ⚠️ **Дополнительная таблица** — outbox в БД
- ⚠️ **Возможны дубликаты** — нужна идемпотентность consumer'а
- ⚠️ **Задержка публикации** — worker работает по расписанию

### Когда использовать
- ✅ Критична гарантия доставки событий
- ✅ Требуется транзакционная целостность
- ✅ Приемлема небольшая задержка (< 100ms)

## Решение 3: HTTP с таймаутом и retry (синхронное улучшение)

Если асинхронная обработка невозможна, улучшаем синхронный подход.

### Плюсы
- ✅ **Простота реализации** — минимальные изменения
- ✅ **Нет дополнительной инфраструктуры** — не нужна очередь
- ✅ **Быстрое внедрение** — можно сделать за час

### Минусы
- ❌ **Не решает корневую проблему** — зависимость от аналитики остается
- ❌ **Возможна потеря данных** — при недоступности аналитики
- ❌ **Нет гарантий доставки** — retry ограничены
- ❌ **Высокая связность** — сервисы все еще зависимы

### Когда использовать
- ⚠️ Временное решение до внедрения очереди
- ⚠️ Очень низкий трафик (< 10 RPS)
- ⚠️ Аналитика работает стабильно 99% времени

## Решение 4: Circuit Breaker Pattern

Защита от каскадных отказов при проблемах с аналитикой.

### Состояния Circuit Breaker

```
        CLOSED
   (normal operation)
          │
          │ failure threshold
          │ exceeded
          ▼
        OPEN
   (reject requests)
          │
          │ timeout period
          │ elapsed
          ▼
      HALF-OPEN
   (trial requests)
          │
          ├─ success threshold ──► CLOSED
          │   met
          │
          └─ failure detected ──► OPEN
```

### Плюсы
- ✅ **Быстрый fail** — не ждем таймаута при проблемах
- ✅ **Защита от каскадных отказов** — изолируем проблемный сервис
- ✅ **Автоматическое восстановление** — пробуем reconnect
- ✅ **Fallback механизм** — можем сохранить в очередь

### Минусы
- ⚠️ **Дополнительная логика** — нужна библиотека и настройка
- ⚠️ **Требует fallback** — нужно куда-то сохранять данные при open state
- ⚠️ **Настройка thresholds** — требует тюнинга под нагрузку

### Когда использовать
- ✅ В комбинации с другими решениями
- ✅ Защита от нестабильных внешних сервисов
- ✅ Требуется graceful degradation

## Решение 5: CDC (Change Data Capture)

Автоматическая публикация изменений из БД в очередь.

### Архитектура

```
┌─────────────────┐
│  PostgreSQL     │
│  ┌──────────┐   │
│  │ orders   │   │
│  │ table    │   │
│  └──────────┘   │
│       │         │
│       │ WAL     │
└───────┼─────────┘
        │
        │ Debezium reads WAL
        ▼
┌─────────────────┐
│   Kafka         │
│  orders.topic   │
└─────────────────┘
        │
        │ consume
        ▼
┌─────────────────┐
│  Analytics      │
│  Service        │
└─────────────────┘
```

### Инструменты
- **Debezium** — CDC connector для PostgreSQL/MySQL
- **Maxwell** — CDC для MySQL
- **pg_logical** — встроенный в PostgreSQL

### Плюсы
- ✅ **Нет изменений в коде** — работает на уровне БД
- ✅ **Гарантия доставки** — все изменения попадают в Kafka
- ✅ **Низкая латентность** — читает WAL в реальном времени
- ✅ **Порядок событий** — сохраняется порядок изменений
- ✅ **Идеально для Event Sourcing**

### Минусы
- ❌ **Сложная инфраструктура** — Kafka + Kafka Connect + Debezium
- ❌ **Нет бизнес-логики** — только сырые изменения таблиц
- ❌ **Сложность отладки** — распределенная система
- ❌ **Требует Kafka** — не подходит для RabbitMQ/NATS

### Когда использовать
- ✅ Уже используется Kafka в стеке
- ✅ Нужна репликация данных в несколько систем
- ✅ Event Sourcing архитектура
- ✅ Большие объемы данных (> 100K events/sec)

## Сравнение решений

| Критерий | Очередь | Outbox | HTTP+Retry | Circuit Breaker | CDC |
|----------|---------|--------|------------|-----------------|-----|
| **Сложность** | 🟡 Средняя | 🔴 Высокая | 🟢 Низкая | 🟡 Средняя | 🔴 Очень высокая |
| **Латентность** | 🟢 < 10ms | 🟡 < 100ms | 🟡 < 2s | 🟢 < 10ms | 🟢 < 50ms |
| **Надежность** | 🟢 Высокая | 🟢 Очень высокая | 🔴 Низкая | 🟡 Средняя | 🟢 Очень высокая |
| **Гарантия доставки** | 🟡 At-least-once | 🟢 Гарантия | 🔴 Best effort | 🔴 Нет | 🟢 Гарантия |
| **Масштабируемость** | 🟢 Отличная | 🟡 Хорошая | 🔴 Плохая | 🟡 Хорошая | 🟢 Отличная |
| **Изменения в коде** | 🟡 Средние | 🔴 Большие | 🟢 Минимальные | 🟡 Средние | 🟢 Нет |
| **Инфраструктура** | RabbitMQ/Kafka | Outbox Worker | Нет | Нет | Kafka+Debezium |

## Рекомендуемое решение: Комбинация подходов

### Этап 1: Быстрое исправление (первый день)
```
OrderService → HTTP + таймаут + retry → Analytics
              └─► Если ошибка → сохранить в БД для retry
```

**Реализация:**
- Добавить таймауты в HTTP client (2 секунды)
- Добавить retry с exponential backoff (3 попытки)
- Отправлять в goroutine, не блокировать ответ пользователю

---

### Этап 2: Среднесрочное решение (неделя)
```
OrderService → Outbox таблица → Outbox Worker → RabbitMQ → Analytics
```

**Реализация:**
- Добавить таблицу `outbox` в БД
- Сохранять события в транзакции с заказом
- Написать Outbox Worker для публикации
- Настроить RabbitMQ

---

### Этап 3: Production-ready решение (месяц)
```
OrderService → Outbox → Worker → RabbitMQ → Analytics Consumer
                                    ▲              │
                                    │              │
                                    └─ Dead Letter Queue
                                            (retry failed messages)
```

**Дополнительно:**
- Circuit Breaker для защиты от каскадных отказов
- Dead Letter Queue для обработки неудачных сообщений
- Мониторинг и алерты (Prometheus + Grafana)
- Distributed tracing (Jaeger, OpenTelemetry)

---

### Мониторинг

**Метрики для отслеживания:**

```go
var (
    orderEventsPublished = promauto.NewCounter(prometheus.CounterOpts{
        Name: "order_events_published_total",
        Help: "Total number of order events published",
    })

    orderEventsProcessed = promauto.NewCounter(prometheus.CounterOpts{
        Name: "order_events_processed_total",
        Help: "Total number of order events processed by analytics",
    })

    orderEventLag = promauto.NewGauge(prometheus.GaugeOpts{
        Name: "order_event_lag_seconds",
        Help: "Lag between order creation and analytics processing",
    })

    analyticsProcessingDuration = promauto.NewHistogram(prometheus.HistogramOpts{
        Name:    "analytics_processing_duration_seconds",
        Help:    "Duration of analytics processing",
        Buckets: prometheus.DefBuckets,
    })
)
```

**Алерты:**
- `order_event_lag_seconds > 60` — задержка обработки > 1 минуты
- `rate(order_events_published_total[5m]) - rate(order_events_processed_total[5m]) > 100` — накопление необработанных событий
- `up{job="analytics"} == 0` — сервис аналитики недоступен

## Ключевые выводы

### Архитектурные принципы:
- ✅ **Асинхронность** — не блокировать критичные операции
- ✅ **Loose coupling** — минимизировать зависимости между сервисами
- ✅ **Fault tolerance** — система должна работать при отказе компонентов
- ✅ **Idempotency** — обработка сообщений должна быть идемпотентной

### Рекомендации:
1. **Краткосрочно:** HTTP + таймауты + retry в goroutine
2. **Среднесрочно:** Outbox Pattern + RabbitMQ
3. **Долгосрочно:** Event-driven архитектура с Circuit Breaker и мониторингом

### Что НЕ делать:
- ❌ Синхронный вызов без таймаутов
- ❌ Блокирование ответа пользователю
- ❌ Игнорирование ошибок аналитики
- ❌ Отсутствие мониторинга и алертов

### Итоговое решение для production:
```
User Request
    ↓
OrderService
    ├─► Save to DB (transaction)
    ├─► Save to Outbox (same transaction) ← Гарантия
    └─► Return success to user ← Быстрый ответ
          
Outbox Worker (background)
    ├─► Read from Outbox
    ├─► Publish to RabbitMQ (with Circuit Breaker)
    └─► Mark as processed

AnalyticsService (consumer)
    ├─► Consume from RabbitMQ
    ├─► Process (idempotent)
    ├─► ACK on success
    └─► NACK on retriable error → Retry
        └─► DLQ on permanent error
```

**Результат:**
- ✅ Заказы не теряются
- ✅ Пользователь получает мгновенный ответ
- ✅ Аналитика обрабатывается асинхронно
- ✅ Гарантия доставки через Outbox
- ✅ Отказоустойчивость через Circuit Breaker
- ✅ Наблюдаемость через метрики и алерты
